## 1. 결론 요약

이전 인식률이 0%에 가까웠던 것은 튜닝 부족이 아니라 **매칭 수식 자체가 정답을 임계값 위로 올릴 수 없는 구조**였기 때문이다. 파라미터를 아무리 조정해도 개선되지 않는 종류의 결함이다.

핵심 근거 한 줄: 정답이 확실한 셀에서 **정답 후보의 점수가 0.4137인데 통과 임계값이 0.60**이었고, 그 정답은 295개 후보 중 **37위**였다. 즉 임계값을 낮춰도 오답이 먼저 나온다.

같은 이미지에 대해 올바른 방식(전경 분리 + 알파 마스크 매칭)을 100줄 남짓으로 프로토타이핑하자 **빈칸 판정 14/14 정확**, 아이템 top-1 약 **65%**가 튜닝 없이 나왔다. 남은 오차의 상당수는 알고리즘이 아니라 **스프라이트 카탈로그 누락**(신규 아이템 30종·석판 7종이 로컬에 없음)으로 설명된다.

**목표 재정의(중요):** "100% 인식"은 임의 스크린샷에 대한 보장으로는 비현실적이다. 대신 다음을 목표로 한다.
- 원본 해상도 PNG 스크린샷: **top-1 99% 이상**
- 그 외(JPEG·리사이즈·스케일링): **95% 이상 + 신뢰도 기반 확인 UI**로 실질 100% 도달

이 구조가 필요한 이유는 §7에 있다.

## 2. 왜 0%였는가 — 측정된 근본 원인

심각도 순. ①이 단독으로 0%를 설명하며, 나머지는 ①을 고쳐도 남는 결함이다.

### ① 히스토그램 정규화 비대칭 — 정답이 임계값을 넘는 것이 수학적으로 불가능

`lib/templateMatcher.ts`의 참조 템플릿과 셀은 **서로 다른 모집단으로 정규화**된다.

| 대상 | 코드 | 정규화 모집단 |
|---|---|---|
| 참조 스프라이트 | `computeHistogram(imgData, hasAlpha=true)` (L48) | **불투명 픽셀만** (`a < 128` 건너뜀, L93) |
| 인벤토리 셀 | `computeHistogram(data, false)` (L143) | **배경 포함 전체 픽셀** |

히스토그램 교집합은 `Σ min(a_i, b_i)`이므로, 셀 히스토그램 질량 중 배경이 차지하는 비율만큼은 **어떤 템플릿과도 겹칠 수 없다**. 따라서

```
달성 가능한 최대 점수 ≈ 셀에서 아이콘이 차지하는 면적 비율
```

실측: 템플릿 불투명 픽셀 비율 **평균 26.0% / 중앙값 24.2%**, 셀 픽셀의 **68~88%가 배경**.
→ 완벽히 일치해도 상한이 약 0.3~0.5인데 `MATCH_THRESHOLD = 0.60`. **정답은 정의상 통과 불가.**

### ② 색 히스토그램은 픽셀아트에서 형태 정보를 전부 버린다

세피리아 아이콘은 팔레트가 극히 작다(`humility_crown` 불투명 영역 **고유색 7개**). 히스토그램은 공간 배치를 버리므로, 팔레트가 비슷한 전혀 다른 아이템이 동일 점수를 받는다. 실측에서 정답 `humility_crown`(0.4137) 위에 `lerids_battleb_racelet`(0.5470), `single_tree_charcoal`(0.5039) 등 **무관한 아이템 5개**가 먼저 왔다.

### ③ `vision.worker.ts`의 템플릿 센터크롭이 아이콘을 잘라낸다

```ts
const TMPL_SIZE = 48
if (cols >= TMPL_SIZE && rows >= TMPL_SIZE) {
  const cx = Math.floor((cols - TMPL_SIZE) / 2)
  tplMat = rgb.roi(new cv.Rect(cx, cy, TMPL_SIZE, TMPL_SIZE)).clone()  // resize가 아니라 crop
}
```

스프라이트는 **80×80 또는 100×100**(실측, 파일마다 다름). 이 코드는 리사이즈가 아니라 **크롭**이므로 80×80에서는 바깥 40%, 100×100에서는 면적의 77%를 버린다. 게다가 셀은 64×64로 리사이즈되어 들어오는데 템플릿은 원본 해상도 조각이라 **스케일이 불일치**한다. `TM_CCOEFF_NORMED`는 스케일 불변이 아니다.

### ④ 마스킹이 아이콘 본체를 지운다

`prepareCellForMatching()`은 `V < 70` 픽셀, **상단 18%**, **하단 15%**, 상단 양 모서리를 검게 칠한다.
- 세피리아 아이콘 상당수가 어두운 색(검은 비늘·회색 돌·어두운 검)이라 `V < 70`에 **아이콘 자체가 삭제**된다.
- 상하 33% 제거는 실제 아이콘 픽셀을 잘라낸다.
- 양쪽 모두 검게 칠한 뒤 `TM_CCOEFF_NORMED`를 돌리면 상관계수가 **검은 영역끼리의 일치**에 지배되어, 검은 영역이 많은 템플릿이 무조건 이긴다.

이 실패 양상은 프로토타입에서도 재현되었다: 마스크 MAE만 쓴 v1에서 `single_tree_charcoal`이 **36칸 중 20칸에서 1위**를 차지했다. 작고 어두운 템플릿이 어두운 배경 위에서 항상 유리한 편향이다.

### ⑤ 아티팩트와 석판을 같은 후보 풀에서 경쟁시킨다

`matchCell()`은 ARTIFACT 295개와 TABLET을 한 배열에 넣고 최대값을 취한다. 두 계층은 렌더링 방식도 배경도 다르므로 서로의 오답원이 된다.

### ⑥ 그리드 검출이 취약

`autoDetectGrid()`는 `l>20 && l<100 && b>=g && r<100` 색 마스크 + 행/열 밀도 투영에 의존하고 `cols: 6`을 하드코딩한다. 실제 스크린샷은 셀 배경이 두 종류(석판 있는 칸 = 청회색, 빈 칸 = 적갈색)이고 바깥에 갈색 프레임이 있어 밀도 투영이 프레임까지 함께 잡는다. `computeCellCrops()`는 균등 분할이라 원점 오차가 6열에 걸쳐 누적된다.

### 2.6 재현 방법

```
scratchpad/repro.py    # ①②의 실측 재현 (정답 0.4137 / 37위 / 커버리지 통계)
scratchpad/proto2.py   # 제안 방식 프로토타입 + 육안 검증 시트 생성
```

## 3. 실증 — 고치면 되는가

동일 스크린샷(`인벤 예시/2.png`, 6×6 = 36칸)에서:

| 방식 | 빈칸 판정 | 아이템 top-1 | 비고 |
|---|---|---|---|
| 현행 코드 (히스토그램) | — | **0%** | 정답 37위, 0.4137 < 0.60 |
| v2 전경분리 + 형태 IoU | **14/14 (100%)** | **약 65%** | 무튜닝, 100줄 |

v2 오답 6건 중 다수(초록 X자 석판, 청·주황 돔형, 초록 기둥 등)는 **로컬에 스프라이트가 없는 신규 아이템일 가능성이 높다**. 즉 알고리즘 오차와 카탈로그 결손이 섞여 있다. 카탈로그를 채우면 실측 정확도는 더 올라간다.

핵심 통찰: **이것은 자연영상 인식이 아니라 결정론적 2D 렌더링의 역문제**다. 게임은 동일 스프라이트를 고정 규칙으로 합성해 그린다. 따라서 렌더링을 재현해 비교하면(analysis-by-synthesis) 원리적으로 거의 정확히 맞출 수 있다. 프로토타입 v3에서 일부 석판은 2위와의 격차가 **+0.53**까지 벌어졌다.

## 4. 목표 아키텍처

```
스크린샷
  │
  ├─ A. 그리드 캘리브레이션   셀 격자·피치·원점을 서브픽셀로 확정
  │
  ├─ B. 셀 분해              칸별 크롭 + UI 오버레이 영역 분리
  │
  ├─ C. 배경 모델링          칸 유형 판정(석판칸 / 빈칸) + 배경 플레이트 추정
  │
  ├─ D. 점유 판정            배경 대비 잔차로 빈칸/아이템칸 이진 분류
  │
  ├─ E. 정합 매칭            알파 마스크 기반, 스케일·오프셋 캘리브레이션 후 고정
  │
  ├─ F. 신뢰도 산정          1위·2위 격차 기반 확신도, 저확신은 후보 3개 제시
  │
  └─ G. 사용자 확정 UI        저확신 칸만 사람이 1클릭 수정 → 실질 100%
```

설계 원칙 4가지:

1. **비대칭 정규화 금지.** 셀과 템플릿은 항상 동일 모집단(템플릿 알파 마스크 내부)에서만 비교한다.
2. **형태를 버리지 않는다.** 히스토그램은 후보 선별(prefilter)에만 쓰고, 최종 판정은 반드시 공간 정합으로 한다.
3. **스케일을 추정하지 말고 캘리브레이션한다.** 한 스크린샷 안에서 아이콘 렌더 스케일은 상수다. 확신도 높은 칸 몇 개로 스케일·오프셋을 1회 추정해 **전 칸에 고정 적용**한다. 이것이 정확도를 크게 올리는 지렛대다.
4. **불확실성을 숨기지 않는다.** 억지로 답을 내지 말고 저확신을 표면화해 G단계로 넘긴다.

### Phase 2 — 그리드 캘리브레이션 재작성

현행 두 경로(`lib/gridDetector.ts` 색마스크, `workers/vision.worker.ts` 컨투어)를 **하나로 통합**한다.

- **2-1.** 셀 테두리의 주기성을 이용한 격자 추정으로 전환. 색 임계값이 아니라 **행/열 방향 자기상관(autocorrelation)으로 셀 피치를 구하고**, 피치에 위상을 맞춰 원점을 정한다. 두 종류 배경(석판칸/빈칸)에 모두 강건하다.
- **2-2.** 균등 분할 누적 오차 제거 — 셀마다 개별 좌표를 갖게 한다.
- **2-3.** 열 수는 하드코딩하지 말고 추정하되 6을 사전확률로 사용.

> 검증: ~~5장 전부에서 검출 격자와 수작업 격자의 셀 중심 오차 ≤ 2px.~~
> **이 기준은 폐기했다** — 픽스처 격자가 같은 방법으로 만들어져 순환이며, 실측에서 px 오차와 실제 정확도가 역상관이었다. 대체 기준: **자동 격자의 end-to-end 인식 정확도가 손라벨 격자 이상.** §9-A 참조. (달성)

### Phase 3 — 매칭 엔진 교체 (핵심)

`lib/templateMatcher.ts`의 히스토그램 경로를 **폐기**하고 다음으로 대체한다.

- **3-1. 템플릿 전처리 재작성.** 알파 바운딩박스로 **타이트 크롭 후 정사각 패딩**(현행 센터크롭 폐기). 80/100px 혼재 문제가 여기서 사라진다. 팔레트 PNG(`mode=P`) 파일이 섞여 있으므로 RGBA 변환을 강제.
- **3-2. 배경 플레이트 추정.** 칸 외곽 링에서 지배색을 추출해 배경 모델 구성.
- **3-3. 점유 판정.** 배경 대비 잔차 비율로 빈칸 분류. *프로토타입에서 이미 14/14 달성.*
- **3-4. 2단계 매칭.**
  - 1단계: 축소 해상도 정합으로 상위 후보 선별 — 단, **단일 스케일 prefilter는 금지**(프로토타입에서 정답이 탈락해 정확도가 무너진 실패 사례 있음). 복수 스케일에서 선별하고 넉넉히 남길 것.
  - 2단계: 알파 마스크 내부에서만 형태 IoU + 색 일치도 결합 점수.

- **3-7. 석판/아티팩트 후보 풀 분리.**
- **3-8. 회전 처리.** `rotate: true` 석판만 4방향 평가.

## 7. 왜 "무조건 100%"를 약속하지 않는가

- `인벤 예시/1.jpeg`는 **JPEG**이다. 손실 압축이 픽셀아트의 팔레트를 훼손한다.
- 사용자가 임의 배율로 캡처·리사이즈하면 보간으로 원본 팔레트가 소실된다.
- 시각적으로 거의 동일한 아이템 쌍이 존재할 수 있다(배지 계열 `diamond_badge`·`garnet_badge`·`topaz_badge` 등 색만 다른 세트가 실제로 신규 추가됨).
- 게임이 또 업데이트되면 카탈로그가 다시 어긋난다 → Phase 1 동기화의 상시화가 필요.

따라서 **높은 자동 정확도 + 저확신 칸 확인 UI**의 조합으로 실질 100%를 만든다. 이 편이 "100% 자동"을 주장하다 조용히 틀리는 것보다 안전하다.

## 9. 미해결 항목

계획 실행 전 확정이 필요하지만, **인식 파이프라인 자체를 막지는 않는** 항목들이다.

- **셀 좌상단 `"2/3"` `"0/4"` `"2/7"` 숫자의 의미 — 미확정.** 정찰 결과는 "슬롯 좌표(row/col)"라고 보고했으나 **반증됨**: 로컬 `slotToKey()`는 하이픈(`row-col`)을 쓰고, 6열 격자에서 `"2/7"`·`"5/5"` 같은 값이 나올 수 없으며, 아이콘이 있어도 숫자가 없는 칸이 존재한다. 실제 의미는 재확인 필요.
- 빈칸의 `"+1"` `"-1"` `"+2"` 오버레이 의미 — 위 항목과 함께 재확인 필요.
- 신규 석판 7종의 한글명.
- 위키 석판 총 60종 여부 — 신규 7종의 CDN 존재는 확인했으나 전체 수는 독립 재검증 안 됨.

이들은 **옵티마이저·효과 계산**에 필요하며 이미지 인식에는 영향이 없다. 인식 작업과 병행해 확정하면 된다.

### 행 수 자동 검출 — 4/5

`rows` 를 주지 않고 `calibrateGrid(img, {cols: 6, scorer})` 를 호출했을 때:

| 이미지 | 실제 행 | 자동+스코어러 | 폴백(스코어러 없음) |
|---|---|---|---|
| 1.jpeg | 5 | **5** | 4 ✗ |
| 2.png | 6 | **6** | 4 ✗ |
| 3.png | 6 | **6** | 4 ✗ |
| 4.png | 6 | **4 ✗** | 4 ✗ |
| 5.png | 6 | **6** | 4 ✗ |

초기 구현은 **5장 전부 3행**을 반환했다(0/5). 원인은 축 비용이 n 에 대해 비교 불가능했던 것 — `gapSum/(n-1)` 은 n-정규화되지만 `dimmest` 는 n개 셀에 대한 min 이라 n 이 커질수록 단조 감소한다. 행 수를 **축 비용이 아니라 완성된 `GridRect` 에 대한 목적함수로** 고르도록 분리하고 Y축에 스팬 하한을 추가해 4/5 가 되었다.

**남은 실패 `4.png`:** y=151 에서 시작하는 정렬이 올바른 4행 부분격자를 택한다(행 1~4를 덮고 0·5를 버림). 3.4% 차이로 이긴다. 근본 원인은 `scoreGrid` 가 셀 점수의 **정규화 없는 합**이라, 빈칸이 18개인 `4.png` 에서는 더 촘촘한 부분격자가 총합에서 이길 수 있다는 것이다. 셀당 정규화는 오히려 악화된다(부분격자를 더 선호). 커버리지/범위 개념이 필요하다.

**중요: 폴백 경로는 행 수를 고를 수 없다(5장 전부 4행).** 스코어러 없이 `calibrateGrid` 를 쓸 경우 `rows` 를 반드시 넘겨야 한다.

### px 오차는 잘못된 성공 기준이었다

계획서가 원래 세운 "셀 중심 오차 ≤2px" 목표는 **폐기한다.** 픽스처의 `grid` 값 자체가 호스트가 같은 방법(무게중심 회귀 + 점수 스윕)으로 만든 것이므로, 그 값에 가까워지는 것은 순환 논증이다. 실제로 최종 라운드에서 px 오차는 평균 6.93px → 8~13px 로 **커졌는데 end-to-end 정확도는 올라갔다**. `3.png` 는 픽스처 격자에서 11.18px 떨어져 있으면서 정확도는 90.9% → 95.5% 로 더 높다. 즉 px 거리와 실제 성능은 이 문제에서 **역상관**이다.

### 격자 검출에서 확인된 사실

- **목적함수가 전부다.** 검출 실패는 탐색 문제가 아니라 목적함수가 오답을 더 높게 평가하는 문제였다. `1.jpeg` 는 좌측 외곽 프레임이 내부 간극보다 어두워(33.95 vs 36.0~36.4) 비용이 역전되면서 격자가 통째로 한 칸 밀렸다(65px 오차). 비용에 **셀 내부 밝기 항**(간극 밝기 − 가장 어두운 셀 내부)을 넣자 정답이 전역 최적이 되면서 1.61px 로 떨어졌다. 평균이 아니라 **최솟값**을 써야 한다 — 평균은 origin 에 따라 매끄럽게 변해 미세 평원을 기울인다.
- **모든 단계를 단조(monotone)로 만들어야 한다.** 초기 구현은 정답 격자에서 출발해도 정답을 떠났다. `4.png` 는 시드가 0.03px 로 거의 완벽했는데 후단이 10.77px 로 망가뜨렸다. 목적함수가 개선될 때만 수용하도록 바꾸는 것이 필수다.
- **죽은 단계는 목적함수가 틀렸다는 신호일 수 있다.** `refineByCentroids` 는 밝기 목적함수에서 5장 모두 기각되어 삭제 후보였으나, 매칭 스코어러로 게이트하자 5장 중 3장에서 채택된다. 삭제하지 않기를 잘했다.
- **행/열별 중앙값 축약이 필수다.** 무게중심 회귀에 평범한 최소제곱을 쓰면 잘못 분할된 셀 하나가 지렛대로 작용해 `3.png` 의 행 pitch 를 12.2px 망가뜨린다(오차 28.8px → 중앙값 축약 후 2.6px).
- **격자 검출 비용**: 이미지당 약 29회 스코어러 호출, 4.3~9.8초. 매처의 `TOPK=28`·9오프셋을 그대로 쓰면 약 30배 느려지므로 스코어러 전용 축소 경로(`TOPK=8`, 오프셋 `[0]`)가 필요하다.

**목표 미달을 분명히 기록해 둔다.** top-1 70.8%는 기준선의 5.7배지만 99%가 아니다. 원인은 두 가지다.

1. **정답 라벨이 48개뿐이다.** 이 시점부터 하이퍼파라미터를 더 만지는 것은 48개 표본에 대한 과적합이다. 실제로 스케일 추정 방식·전경 임계값·크롭 여백을 여러 조합으로 스윕했지만 66~71% 구간에서 진동했고, 이 차이는 표본 수를 고려하면 통계적으로 의미가 없다. **더 필요한 것은 파라미터 탐색이 아니라 정답 데이터다.**
2. **스케일 잠금이 이미지마다 흔들린다.** 네 PNG는 셀 피치가 119~121px로 사실상 같은데도 잠금 스케일이 42/42/34/40으로 갈렸고, 34로 잠긴 `4.png`가 가장 나빴다. 셀을 64px 캔버스로 정규화하므로 스케일은 렌더링 상수여야 한다는 가설로 전역 고정도 시도했으나 오히려 60.4%로 떨어졌다 — 즉 이미지별 적응이 스케일 외의 다른 편차까지 흡수하고 있다. 이 부분은 아직 원인이 규명되지 않았다.

### 99%까지 남은 일 (우선순위 순)

1. **정답 라벨 확대** — 현재 48개. 최소 150개는 있어야 개선 여부를 신뢰할 수 있다. `1.jpeg` 무손실 재캡처 + 신규 스크린샷 확보가 가장 효과가 크다.
2. **스케일 추정 원인 규명** — 왜 전역 고정이 이미지별 적응보다 나쁜지 아직 모른다. 아래 두 가설은 이미 시험해서 **기각**했으니 반복하지 말 것.
   - *기각 ①: 전역 고정 스케일.* 셀을 64px 캔버스로 정규화하니 아이콘 스케일은 렌더링 상수일 것이라 보고 36~46을 전역 고정해 봤다. 최고 60.4%로, 이미지별 적응(70.8%)보다 나빴다.
   - *기각 ②: 전체 캔버스 정규화.* 확정 라벨의 스프라이트를 재보니 알파 bbox 크기가 **47~70px로 제각각**이었다(80×80/100×100 캔버스 안에서). 타이트 크롭 후 정사각 정규화가 아이콘의 상대 크기 정보를 지운다고 보고, 원본 캔버스 전체를 고정 배율로 렌더하는 방식을 시험했다. 최고 58.3%(FORCE=58)로 역시 더 나빴다. 즉 게임이 스프라이트 캔버스를 균일 배율로 그리는 것은 아니거나, 위키 스프라이트의 캔버스 프레이밍이 일정하지 않다.
   → 다음 시도는 추측이 아니라 **한 장에서 아이콘 렌더 크기를 원본 픽셀로 직접 실측**해 셀 피치와의 관계를 확정하는 것이어야 한다.
3. **석판 회전 처리 재검토** — 회전 가능 석판이 많은 `5.png`가 가장 나쁘다. 회전 변형 4종이 후보 공간을 넓혀 오답을 늘리는지 확인 필요.
4. **§5 3-6 편향 보정 미구현** — 작고 어두운 템플릿 편향 정규화는 아직 들어가지 않았다.

## 9-F. 격자 검출 완성 — 행 수 7/7, 자동 격자가 손라벨과 동률

### 결과

| 격자 | 빈칸 | top-1 | 종합 |
|---|---|---|---|
| 손라벨 (대조군) | 96.6% | 65.5% (95/145) | **75.0% (156/208)** |
| **자동 + 스코어러** | **98.1%** | 64.1% (93/145) | **75.0% (156/208)** |
| 자동, 스코어러 없음 | 96.6% | 53.1% (77/145) | 67.3% (140/208) |

**행 수 자동 검출 7/7** (이전 5/7). 사용자가 행 수를 알려주지 않는 실사용 경로가 이제 전 픽스처에서 동작한다.

### `scoreGrid` 는 정규화하지 않는 것이 옳았다

호스트는 "정규화"를 지시했지만, 측정 결과 **셀당 평균은 부분격자를 더 선호**한다(0.0457 vs 0.0294). 합(sum)이 옳은 집계자다 — 합 자체가 커버리지를 보상하기 때문이다. 문제는 집계 방식이 아니라 **부분격자라는 특정 실패 모드**였고, 그건 가중치 혼합이 아니라 **셀 단위 커버리지 규칙**으로 잡는 게 맞다.

채택한 것: `missedOutside(rect)` — 후보 격자 바로 위·아래 행에 점유 셀이 몇 개 있는지 센다. 행 수는 **사전식**으로 고른다(놓친 셀 최소 우선, 매칭 점수는 동점 처리). **조정 계수가 없다.** 신호가 선명하다.

```
정답 격자는 7장 전부 missed=0
4.png  n=4 score 1.0964 missed=1   <- 이전 승자, 이제 배제
       n=6 score 1.0600 missed=0   <- 정답
6.png  n=4 score 2.6215 missed=5   <- 이전 승자, 이제 배제
       n=5 score 2.3750 missed=0   <- 정답
```

### 진짜 개선은 다른 곳에 있었다

end-to-end 정확도(+4셀)는 커버리지가 아니라 **스윕의 도달 범위**에서 나왔다. 기하 오차가 최대 ±11px 인데 `SWEEP_DX` 는 ±4 까지만 닿아 **구조적으로 보정이 불가능**했다. 고정 5×5 스윕을 **수렴형 좌표하강**(개선이 없을 때까지 반복, 단조 유지)으로 바꾸자 해결됐다.

교훈: 목표를 못 맞출 때 목적함수부터 의심하기 전에 **탐색 반경이 정답을 포함하는지** 먼저 확인할 것.

### 기각된 것들 (과적합 회피)

- **n별 사전 정렬**: 구현해서 측정했으나 7장 × 후보 4개 중 **단 1개**의 후보만 바뀌었고(경쟁에 없던 후보) 결과는 동일. 죽은 복잡도라 제거했다. "n=6이 자기 최적점에서 평가되지 않는다"는 호스트 가설은 합리적이었으나 측정이 반증했다.
- `SWEEP_ROUNDS=2` 는 157/208 로 **1셀 더 좋았지만 채택하지 않았다.** 208개 중 1셀은 잡음이고, 그걸 고르는 것은 픽스처 튜닝이다. 라운드 4와 8이 동일 결과라 상한은 구속 조건이 아니다.
- `SCORER_SWIN=2` 는 1.67배 빨랐으나(102초→61초) 품질이 떨어져(행 5/7→4/7) 기각.

### 커버리지 프로브 보강 — 빈 마지막 행 맹점 제거

첫 구현(`missedOutside`)에는 실사용에서 자주 밟을 구멍이 있었다. **참 격자의 마지막 행이 통째로 비어 있으면** 한 행 작은 후보도 실제 아이템을 바깥에 남기지 않아 `missed=0` 으로 동점이 되고, 판정이 다시 비정규화 합으로 되돌아간다. `4.png` 가 정확히 이 경우였고 마진이 **3.0%** 에 불과했다. 인벤토리가 덜 찬 상태는 흔하므로 픽스처 우연이 아니다.

수정: 프로브 셀을 "점유됨" 뿐 아니라 **"테두리 링이 격자 자신의 셀들과 일치함"**(= 프레임이나 배경이 아니라 **빈 인벤토리 칸**)일 때도 센다. 기준자는 격자 자신의 링 편차라 **조정할 임계값이 없다.** 결과가 3% 마진에서 범주적 분리로 바뀌었다.

```
참 격자는 7장 전부 panelLike = 0
2.png  n=5 → 6   n=6(정답) → 0     (이전에는 0 vs 0, 점수로 판정)
4.png  n=5 → 6   n=6(정답) → 0     (이전 마진 3.0%)
6.png  n=3 → 6   n=4 → 6   n=5(정답) → 0
```

부수 효과로 **스코어러 없는 폴백의 행 수 검출이 3/7 → 6/7** 로 올랐다(이 프로브는 스코어러가 필요 없다). 그리고 동점이 일찍 깨져 스코어러 호출이 줄어 **스위트가 97.3초 → 92.7초로 빨라졌다.**

### 회귀 방어선을 픽스처 단위로 내렸다

집계 floor 하나로는 재분배를 못 잡는다는 것이 실제로 확인됐다 — auto 경로에서 `6.png` 가 4셀 회귀했는데 `7.png`(+5)와 `5.png`(+4)가 상쇄해 TOTAL 은 그대로였다. 이제 **픽스처별 top-1·종합 하한**을 프리즈 경로와 auto 경로 양쪽에 걸었고, 각 픽스처의 `it` 안에서 단언하므로 회귀가 **어느 스크린샷인지 이름을 대며** 실패한다.

### 남은 것

- 자동 격자가 **top-1 에서는 여전히 대조군에 뒤진다**(93 vs 95). 종합이 같은 이유는 아이템 식별 2개를 빈칸 판정 2개와 맞바꾸고 있기 때문이다.
- **`6.png` 의 auto 회귀(22/30 → 18/30)는 복구되지 않았다.** 픽스처별 floor 로 더 나빠지는 것은 막았지만 원인은 미해결이다. 기하 오차도 7장 중 최대(평균 16.39px)다.
- **폴백 경로의 행 수 검출은 6/7** (`7.png` 만 실패). 스코어러 경로는 7/7.
- `scoreGrid` 가 7장 전부에서 손라벨 정답보다 검출 격자를 높게 평가한다. **프록시가 정확도와 완전히 정렬되어 있지 않다**는 뜻이며, 격자 목적함수의 남은 개선 여지다.
- 기하 px 오차는 오히려 커졌는데(4.png 7.41→13.44px) 정확도는 올랐다. **px 거리가 잘못된 지표라는 세 번째 확인**이다.
- 스위트가 97.2초로 120초 예산에 근접했다. 스코어러 기반 캘리브레이션을 픽스처당 하나 더 추가하면 초과한다.

## 9-B. 보류한 저위험 결함 (Sentinel 리뷰, 미수정)

이번 웨이브에서 의도적으로 다루지 않았다. 전부 현재는 미발현이거나 완전 동점 상황에서만 영향이 있다.

- **동점 시 후보 선택 순서가 레퍼런스와 다르다.** 레퍼런스는 `np.argpartition`(동점 순서 미정의) + Python set 순회, TS는 전체 정렬. 추가로 `harness.ts` 의 `readdirSync` 는 정렬을 보장하지 않아 variant 인덱스 순서가 플랫폼 의존이다. 점수가 완전히 같을 때만 갈린다.
- **`newreg` 누산 정밀도.** numpy는 float32, TS는 float64. 상대오차 ~1e-7로 근소 동점을 뒤집을 수 있다.
- **`sharp` 출력 채널·깊이 미검증.** `.ensureAlpha().raw()` 가 RGBA8 이라고 가정한다. 그레이스케일 PNG는 2채널, 16bit PNG는 채널당 2바이트를 반환하므로 그런 자산이 하나만 섞여도 전 템플릿이 조용히 깨진다. 현재 327개 전부 RGBA8 이라 미발현.
- **`ringScratch`/`ringSeen` 이 모듈 전역 가변 상태**라 `analyzeCell` 이 재진입 불가하다. 두 recognizer 를 동시 실행하면 오염된다. 현재 핫패스에 `await` 가 없어 안전.

## 10. Phase 0에서 새로 확인된 사실

계획 수립 시점에는 몰랐고, 실제로 구현·측정하면서 드러난 것들이다. Phase 2·3 설계에 직접 반영해야 한다.

### 10-1. 격자 자동 검출은 생각보다 어렵다 — 세 방법 모두 실패

- **에지 에너지 투영**: 바깥 프레임을 셀 경계로 오인. `2.png`에서 `originY`를 실제보다 11px 위로 잡았다.
- **어두운 간극(gap) 피팅**: 격자 맨 바깥 선에는 대응하는 간극이 없어 편향된다. 내부 선만 쓰도록 고쳐도 `1.jpeg`에서 발산했다.
- **색 기반 연결요소**: 셀 내부(V≈73)와 프레임(V≈116), 빈칸(V≈98)의 명도가 너무 가까워 분리 불가.

**성공한 방법(Phase 2에 채택할 것):** 전경 무게중심 회귀 + 매칭 점수 스윕의 2단계 자기 캘리브레이션.
셀별 전경 무게중심의 셀 중심 대비 편차를 행·열 인덱스에 회귀시키면 기울기가 pitch 오차, 절편이 origin 오차가 된다. 이걸 3회 반복해 pitch를 잡고, 남은 상수 편차는 실제 매칭 점수를 최대화하는 origin 스윕으로 제거한다. 5장 전부에서 육안 검증을 통과했다.

### 10-2. 매칭 점수 설계에서 반드시 피해야 할 함정 세 가지

실제로 겪은 실패다. 재현 가능하다.

1. **단일 스케일 coarse prefilter 금지.** 축소 해상도 1스케일로 상위 후보를 거르자 정답이 그 단계에서 탈락해 정확도가 무너졌다(`single_tree_charcoal`이 36칸 중 20칸에서 1위). 복수 스케일에서 넉넉히 남겨야 한다.
2. **UI 텍스트 영역은 양쪽 마스크에 동일하게 적용할 것.** 셀 전경에서만 상단 텍스트 띠를 잘라내고 템플릿 마스크에는 적용하지 않으면, 위로 긴 아이콘이 구조적으로 불리해진다. 유효 영역(VALID)을 정의해 **셀과 템플릿 양쪽에서 동일하게** 제외해야 한다. 이걸 고치기 전에는 정답이 대부분 2~4위에 머물렀다.
3. **배경은 단일 색이 아니라 다색 모델이어야 한다.** 석판 칸 배경에는 마름모 패턴이 있어 중앙값 한 색으로는 패턴이 전경에 남는다. 테두리 링 색을 양자화해 4% 이상을 차지하는 색 계열을 전부 배경으로 삼아야 한다. 단일 중앙값으로 바꿨을 때 빈칸 판정이 16/16 → 11/16으로 무너졌다.

### 10-3. 작고 어두운 템플릿 편향은 실재한다

`unalloyed_gold_needle`(신규 아티팩트)이 기준선 오답의 최다 출현 항목이다. 마스크 면적이 작고 어두운 템플릿은 어두운 배경 위에서 거의 항상 높은 점수를 받는다. §5 3-6의 정규화를 형식적으로 두지 말고 **반드시 구현하고 회귀로 검증**할 것.

### 10-4. 점유 판정은 어두운 아이콘에서 실패한다

전경 비율 임계값만으로는 **어두운 보라색 구체** 같은 아이콘을 빈칸으로 오판한다(`3.png` 슬롯 8, `5.png` 슬롯 30에서 실제 발생). 반대로 빈칸의 `+1`/`-1` 오버레이 텍스트는 전경으로 오인될 수 있다(`5.png` 슬롯 20). 밝기 기반 단일 임계값이 아니라 **배경 색 분포로부터의 거리 + 연결 성분 크기**를 함께 봐야 한다.

### 10-5. 프로토타입 실측 (참고)

호스트 프로토타입(전경분리 + 형태 IoU + 색 일치, 캘리브레이션 격자, 327 템플릿)으로 `2.png`에서:
- 빈칸 판정 **16/16 정확**
- 아이템 top-1 **약 85%** (20칸 중 17칸)

기준선 12.5% 대비 큰 폭의 개선이며, §5 Phase 3의 목표(≥99%)가 도달 가능한 범위임을 뒷받침한다. 다만 이는 한 장에 대한 육안 채점이므로 정식 지표가 아니다 — Phase 3에서 하네스로 정식 측정할 것.
